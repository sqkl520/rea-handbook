# 案例研究

> 三个真实分析。全部静态完成（不执行目标程序）。
> 这些案例展示了 REA 在真实场景下能产出什么级别的结果。

本目录既有**摘要**（就是本文件），也有**完整报告**：

| 摘要 | 完整报告 | 目标 |

## 为什么放案例研究

官方文档讲的是"能做什么"——命令、参数、能力清单。
但工具的真实价值不在能力列表里，而在**产出物的形态**：一份 REA 分析最终会长成什么样？
哪些结论是它替你做出来的，哪些还得自己动手？在多大的目标上它开始力不从心？

这三个案例是对这些问题的直接回答，也是本手册里最接近"一手证据"的部分：

- **规模上跨越两个数量级**：5.5 MB 的单文件 .NET 应用 → 146 MB 的 Electron 归档（应用图谱完整产出；semantic 层达 100,000 节点上限后截断，`status: partial`）→ 567 MB 的巨型归档（部分完成）
- **技术上覆盖两条完全不同的分析路径**：.NET IL 静态分析与 JavaScript / Electron 静态重建
- **都是为"学习设计思想"而做的**，不是为找漏洞——报告里记录的是架构、设计模式和工程取舍

有一点贯穿三个案例：**结论都经过交叉验证**。REA 的 evidence 是机器可读的中间产物，
从 evidence 到人读报告之间，有一次由分析者把关的"翻译"。
三个案例里我们都踩过"名字的误导"，最后的结论全部回到源码或反编译产物核实过。

## 案例一：PCL2 —— 从 IL 里读出一个启动器的完整架构

> **分析声明**：本分析基于公开获取的软件发行包，使用静态分析方法（不执行目标程序、
> 不绕过任何技术保护措施），目的是学习软件设计思想。
> 报告中的代码片段为分析中整理/重写的示意，版权归原作者。

**目标**：Plain Craft Launcher 2 v2.13.1.1（WPF + VB.NET，.NET Framework 4.0；文件名里的 "2.1" 是误导）
**规模**：5.5 MB 单文件 / **643 个类型、6,116 个方法、3,503 个字段** / 23 个程序集引用 /
仅 8 个 P/Invoke 系统 DLL——网络全部走 .NET 托管栈，是一个纯托管应用
**用了什么**：REA 的 .NET 静态分析（`inspect-managed-*`）+ `ilspycmd` 全量反编译 +
自写 PE/CLI 元数据解析器（13 个脚本）+ BAML→XAML 解码 + `#US` 字符串堆解析
**产出**：**3,600+ 行 / 14 章 / 65 小节**的主报告（合规整理后的版本；原始产出为 69 小节）；配套 163 文件约 90K 行反编译源码、
59 个 BAML 转出的可读 XAML、84 个类型的 CIL 提取

**最值得说的 5 个发现**：

1. **`Loader*` 可组合任务树**（§5）
   启动器所有耗时操作——下载、安装、启动、资源检查——全部跑在同一套自研任务框架上。
   每个节点带 `_ProgressWeight`，父进度 = 子进度的**加权平均**（"下载 100 个小文件 + 1 个大文件"
   的进度条不会被小文件占满）；后台线程事件与 UI 事件是**两条独立通道**（从框架层面消灭
   "后台线程更新 UI"这类错误）；取消基于 `CancellationTokenSource` 沿树传播。
   它把"可能失败、可取消、带进度、分阶段的长任务"抽象成了一个可组合类型。

   ```text
   LoaderBase（抽象节点：状态机 + 加权进度 + 双通道事件 + 取消）
   ├── LoaderCombo(Of T)        —— 组合节点，GetLoaderList 延迟展开子任务
   ├── LoaderTask(Of TIn, TOut) —— 叶子节点，InputDelegate / LoadDelegate 两阶段
   └── LoaderWorker             —— 唯一真正碰线程的类
   ```

2. **主题 = HSL 算法，不是色板**（§9.2）
   每个主题只定义三个数：`(色相, 饱和度, 明度微调)`。真正有意思的是它共享一条
   **14 段感知校正曲线**：按色相 30° 一段对明度阈值做插值修正，解决"黄色看起来比蓝色亮"
   的知觉问题——先算出视觉上等效的明度，再生成整套色板（8 级灰阶 + 主题色）。
   加一个新主题 = 加三个数。

   ```text
   色相 → 14 段校正表插值（按 30° 分段）→ 重映射明度 → 标准 HSL → RGB → 整套色板
   FromHSL2(色相, 饱和度, 明度)   ← 应用感知校正（概念示意，整理重写）
     └─ FromHSL(色相, 饱和度, 校正后明度)
   ```

3. **自研 XAML 沙箱**（§11）
   它的扩展系统允许从远程 URL 加载 XAML 当主页——这是一个真实的远程内容加载面，
   所以作者写了一个消毒器：**8 个禁止类型**（内嵌浏览器、导航、媒体、能调任意方法的
   `ObjectDataProvider`、能递归加载的 `XamlReader`、开新窗口、XML 数据绑定、直读写设置的内部类型）
   + **3 个禁止成员**（`Code` / `FactoryMethod` / `Static`）。
   关键实现细节：用 `XamlXmlReader` **遍历 token 流**逐一检查（不是文本正则，编码变形绕不过去），
   并且把 `XamlReader` 本身列入禁止表，堵住"外层合法、内层未检查"的递归漏洞。

4. **崩溃诊断三层策略**（§8）
   **46 个原因枚举**、约 90 条规则（字面量主表约 70 条 + 加载器自报 + 低置信度补充 +
   堆栈关键词分析）。结论带**置信度分级**——"确定是 X 导致" / "怀疑是 X 导致，但不能完全确定" /
   "机制性解释"，每条结论都附带**可执行建议**。堆栈分析里最精巧的是两层包名黑名单
   （20 项包名前缀 + 106 项技术通用词，剩下才可能是 Mod 的独特包名），
   外加"提取出超过 10 个候选就熔断"——宁可不报，也不误导。

5. **版本隔离的三重兜底**（§3.2）
   决定"这个版本的工作目录是否隔离"时，按顺序尝试三条路径：
   ① 从旧版设置迁移（升级不丢偏好）→ ② **从文件布局反推用户意图**
   （这个版本目录下已经有 `mods/`、`saves/`，说明用户期望隔离）→ ③ 全局五档默认策略。
   判定结果持久化，推断只发生一次。这是"迁移逻辑"的一个漂亮样板：
   **先理解用户已经做了什么，再决定默认值**。

**这个案例教了什么方法论**：

- **字符串即文档**。成熟应用的日志文案是自带文档。PCL2 把执行日志当字符串常量内联，
  扫出 **101K 条 UTF-16 串 + 6,358 条 `#US` 字面量**后，日志文案的**顺序就是执行流程的顺序**
  （"分析支持库文件" → "下载支持库文件" → "分析资源索引" → "下载资源索引"）。
  本案例绝大部分结论的第一条线索都来自这些字符串。注意必须按 UTF-16LE 解码，否则中文全丢。
- **调试路径泄漏是金矿**。发布版没有剥离 `CallerFilePath` 调试信息，从 `.text` 段还原出
  **52 条源码路径**，直接重建了完整目录树——它让"类型名 → 源码文件 → 目录归类"这条链完全闭合，
  也意外证实了自更新走差分更新（微软 MSDelta）、更新包验签（ECDSA P-256）等推断。
  对开发者是"编译时该剥离"的提醒；对分析者是理解架构的最快入口。
- **反编译优先（.NET 场景）**。`ilspycmd -p` 全量反编译一次产出 163 个文件的可读源码，
  是本案例最有威力的一步。反编译语言可能与原文不同（VB.NET → C#），但命名与结构准确。
- **工具卡住时，直接写解析器**。REA 的全量成员提取会因元数据超表示预算而拒绝，
  官方给的正路是"按类型名逐个提取"——但前提是你**已经知道类型全名**。
  我们因此自写了 PE/CLI 元数据解析器来先拿到类型清单。这一步是 .NET 分析真正的门槛。
- **交叉验证，因为名字会骗人**。`PageLinkMain` 看着像主页，实际是联机页
  （私有字段 `NATType` / `NetworkSecret`，邀请码由 `GetInviteCode()` 现拼）；`MySkin` 看着像主题引擎，实际是 Minecraft 皮肤预览控件。
  **看字段和方法，不看名字**——关键的类型归属结论必须回到反编译源码核实。

完整报告 → [pcl2.md](pcl2.md)（约 3,600 行，14 章）

## 案例二：ChatGPT 桌面版 —— 一个 567 MB 前端的工程做法

> **分析声明**：本分析基于公开获取的软件发行包，使用静态分析方法（不执行目标程序、
> 不绕过任何技术保护措施），目的是学习软件设计思想。
> 报告中的代码片段为分析中整理/重写的示意，版权归原作者。

**目标**：ChatGPT 桌面版 26.1007.2314.0（MSIX 打包，显示名 "ChatGPT"；标准 Electron 应用）
**规模**：`app.asar` **567 MB** / 外壳 `ChatGPT.exe` 仅 4.7 MB + `chrome.dll` 329 MB
（Electron 打包的 Chromium 155）/ 最大 JS bundle 10.9 MB
**用了什么**：REA 静态应用重建（**部分完成**——分析到 3,757 / 16,197 个源文件时
父进程结果容量耗尽，返回部分结果并明确标注）+ 自写 ASAR / CSS / IPC 解析脚本（10 个）。
**报告主要结论来自直接解析 ASAR**
**产出**：UI 架构分析报告 + 可复跑的 10 个解析脚本。分析中途还纠正了一个初始误判——
它不是"Chromium 内嵌 shell"，是标准 Electron 应用（主进程 bundle 里有 134 处 `BrowserWindow`、
20 处 `ipcMain`）

**最值得说的 5 个发现**：

1. **44 个命名容器查询**（§2，整个分析里最有价值的一处）
   UI 的自适应主力是 **CSS 容器查询**（`@container`）而不是媒体查询——组件按**自己所在容器的宽度**
   自适应，同一个卡片放在侧边栏（窄）和主区域（宽）会自动呈现不同布局，不需要任何 JS。
   实测：**190 个容器规则 vs 83 个媒体查询**，媒体查询只留给真正与设备相关的场景
   （`hover`、`forced-colors`、`prefers-reduced-motion` 等）。
   44 个容器名直接暴露产品结构：`app-shell-*`（应用外壳）、`page-*`（页面体系），
   还有 `flashcard-editor`、`sketch-canvas`、`site-preview` 这类生成式 UI 产物的编辑器。

2. **三层设计令牌**（§3）
   2,035 个 CSS 自定义属性分三层：语义令牌（组件只消费这一层）→ 应用主题（可整体替换）→ 原始值。
   好处是换主题只需重定义第二层，121 个组件一行都不用改。
   其中 **413 个 `--vscode-*` 变量**很有意思——它主动读取 VS Code 的编辑器字体设置
   （`--vscode-editor-font-family` 等），把自己当作"编辑器生态的一员"而不是独立应用。

3. **集中式 IPC 通道常量表**（§6）
   跨进程通道名**不是散落的字符串字面量**，而是集中在 bootstrap 模块的常量表里按命名空间组织——
   实测提取出 **23 个 `codex_desktop:*` 通道**，还有 `worker:${id}:{from,for}-view` 这样的
   **动态工厂**（每个 worker 实例分配一对专属通道）。这解释了为什么简单正则扫描会全部落空。
   另一个工程细节：每个 handler 的第一行都是可信来源校验（`isTrustedIpcEvent`）。

4. **Rust 工具链**（§1）
   从产物痕迹反推的构建管线：**rolldown**（Rust 打包器，Vite 6+ 的新默认）+
   **lightningcss**（Rust CSS 处理管线，产物里留有 714 个 `--lightningcss-*` 变量）。
   19,000+ 个资源、567 MB 的归档用 JS 工具链构建会很痛苦，所以选了 Rust 系——
   这也解释了安装包体积：大量东西是**预编译进产物**的，而不是运行时加载。

5. **前端跑完整 .NET WASM 运行时**（§4）
   assets 里有 **31 个 wasm 模块**，包括 `System.Private.CoreLib`（.NET 运行时核心）和
   `DocumentFormat.OpenXml`（4.18 MB，Office 文档格式库）。
   推论：Office 文档生成 / 编辑在前端用 .NET 编译成 WASM 本地跑，不走服务端。
   这是"能力本地化"策略的极端体现——SQLite、终端、文档处理全部放在本地。

**这个案例教了什么方法论**：

- **大目标必须先投影，不要直接读**。567 MB 的 evidence 直接读必然出问题；
  REA 的路径是"生成时就过滤（`--filter-output`）→ summary 视图 → 模块页"。
  同时注意投影工具自身：这个体量要走流式处理（如 `jq`），
  一次性 `readFileSync` 会撞上运行时单字符串约 512 MiB 的硬上限。
- **超大规模下"部分结果"是正常终点**。REA 在容量耗尽时返回已完成的部分并明确标注
  （`coverage.status = partial`），**不假装成功**——报告把这一点原样写进去了。
  诚实标注让"结论仍然可用"和"证据链完整"这两件事可以分开评估。
- **结论可以不依赖 REA 的图谱**。本案例报告的主要结论（容器查询、设计令牌、通道表）
  来自直接解析 ASAR，删掉 evidence 文件结论依然成立——图谱是加速器，不是依赖。
- **数字必须带口径**。同一个归档有三个都对的数字：归档全部文件 **20,988** /
  webview 资源 **19,406** / 可解析源文件 **16,197**，它们分别对应
  "归档里有什么"、"UI 资源有多少"、"静态分析实际解析了多少"。**不写口径的数字等于没写。**
- **正则落空 ≠ 不存在**。通道名经压缩后被别名化、且集中在常量表里，直接正则必然落空。
  正确路径是顺着 `require` 找到定义模块，再搜反引号字符串。
  这类"先找调用形态、再找名字在哪定义"的思路，是两个 Electron 案例共享的核心技巧。

完整报告 → [chatgpt-desktop.md](chatgpt-desktop.md)

## 案例三：OpenCode —— REA 跑完整的一场，IPC 双端闭环

> **分析声明**：本分析基于公开获取的软件发行包，使用静态分析方法（不执行目标程序、
> 不绕过任何技术保护措施），目的是学习软件设计思想。
> 报告中的代码片段为分析中整理/重写的示意，版权归原作者。

**目标**：OpenCode 桌面版 0.1.18（Electron）
**规模**：`app.asar` **146 MB**；REA 重建出的应用图谱 **27,278 节点 / 32,977 边**；
解析 JS 文件 4,489 个、AST 节点 475 万；evidence 354 MB
**用了什么**：REA 静态应用重建（**146 MB 应用图谱完整产出**——"中等规模目标 REA 最合适"的实测基准点；
注意 semantic 层达 100,000 节点上限后截断，`status: partial`）
+ 功能追踪（`trace-application-feature`）+ 3 个自写脚本
**产出**：分析报告 + 一份 **4.8 KB 的追踪摘要**（结论级资产）——
摘要本身在仓库里：[`evidence/trace-summary.json`](evidence/trace-summary.json)，
上面那些数字可以直接从它读出来（`node verify-handbook.mjs` 的【7】节会核对两边是否一致）

**最值得说的 5 个发现**：

1. **IPC 双端精确闭环**（本案例最有价值的部分）
   REA 自动把渲染进程侧的 `invoke` 与主进程侧的 `handle` **按通道名精确配对，
   且两侧都带源码行列号**：

   ```text
   kill-sidecar 通道
     渲染进程侧：out/preload/index.js   第 11 行    invoke
     主进程侧：  out/main/index.js      第 2069 行  handle（inline-function）
   ```

   这是静态分析少见的能力——跨进程的调用关系一般是"知道两端存在、但连不起来"，
   这里连到了行号。

2. **完整的 IPC 规模画像**
   ```text
   163 个 IPC 操作 | 76 个字面量通道 | 81 个主进程 handler
   65 个 renderer invoke ↔ 77 个 main handle
   13 个 renderer 监听 | 59 个暴露的 API 成员
   ```
   把它和案例二对照：OpenCode 的通道名是**字面量**，所以好提取；
   ChatGPT 桌面版的通道名藏在常量表 + 动态工厂里。两个案例的对比本身就是一份
   "IPC 通道名提取方法"的教学。

3. **5 个原生插件交接点**（诚实标注"静态分析到头的地方"）
   追踪 `kill-sidecar` 时发现 5 个 `.node` 原生模块（`@parcel/watcher`、`node-pty`、
   `msgpackr-extract` 等）——再往下需要原生分析引擎。报告把这些点**明确标了出来**，
   而不是含糊过去。另外还识别出了同步通道的形态：`ipcMain.on(ch, e => e.returnValue = ...)`
   （对比异步的 `handle`）。

4. **一个子系统的完整设计规范**（WSL 服务器管理）
   ```text
   14 个通道 / 41 条 IPC 记录
   渲染侧全是 invoke、主侧全是 handle
   配一对 subscribe / unsubscribe 事件流
   ```
   可以把它当成"Electron 应用内一个完整功能子系统"的参考设计来读：
   通道命名、方向约定（谁调谁）、事件流配对，一应俱全。

5. **Electron fuses 状态一次调用拿全**
   `inspect-electron-fuses` 秒级给出各安全开关（asar 完整性校验、`RunAsNode` 等）的当前取值，
   作为一份中性的**打包配置画像**记录在报告里。

**这个案例教了什么方法论**：

- **它也是"规模基准点"**。同一套流程在 146 MB 上完整产出应用图谱（semantic 层截断于节点上限）、在 567 MB 上部分完成——
  "REA 静态分析适合中等规模目标"这个结论，就是从这两个案例的对比里得出的。
- **功能追踪的 seed 用字面量字符串（`string`）**。按通道名追功能时，
  直接用通道身份作 seed 会返回 no-match（通道名存在观测属性里，不在节点身份上）；
  换成字面量 `string` 即命中。命中 2 个种子后展开出跨 27,278 节点、
  7,823 条终端路径的可达子图。
- **区分"结论级资产"与"可重跑资产"**。`trace-summary.json` 只有 **4.8 KB**，
  却记录了"2 命中 / 27K 节点 / 5 个原生交接点"这个结论，值得长期保留；
  354 MB 的完整图谱随时可以重跑，删掉不会让报告失效。
- **ASAR 完整性校验失败是常态**。打包工具会在写完归档头之后对 `.asar.unpacked` 里的
  原生二进制二次签名，所以校验失败（`artifact_integrity_mismatch`）属正常现象；
  加 `--integrity-policy record-and-continue` 继续分析，矛盾记录会保留在结果里供复核。

完整报告 → [opencode.md](opencode.md)

## 三个案例的共同点

**1. 同一条方法链路**。三个案例走的是同一套流程：

```text
侦察（确认技术栈，选分析路径）
  → 字符串 / 清单先行（日志文案、URL、通道名 —— 产出/成本比最高的一步）
  → 大目标投影（filter-output / summary 视图）
  → 按功能维度切分（按功能链路组织，不按文件顺序）
  → 交叉验证（关键结论回到源码 / 反编译产物核实）
  → 诚实标注（observed vs 推断；部分完成就写部分完成）
```

> **标注制度对照**：本目录的三个案例报告用自然语言标注——
> "**实测**" = 教学模板中的【观测】（直接看到源码/反编译/字符串原文）；
> "**推测/推断**" = 教学模板中的【推断】（根据结构/命名推断）。
> 指南文档（`guides/`）用【实测】/【官方】两档。三套是同一思路的不同措辞。

**2. 都用 REA + 自写脚本的组合**。分析期三个案例合计写了 26 个 `.cjs` 脚本，
其中 **15 个已收进本仓库的 `tools/`**（其余是只对特定目标有效的一次性脚本，没有通用价值）——
分工很明确：
**REA 提供结构化证据链**（跨文件关联、IPC 双端配对、行列号），
**脚本补工具盲区**（元数据超预算、ASAR 头部解析、集中式通道表）。
反编译（`ilspycmd`）作为 REA 之外的验证手段，也是这个组合的一部分。

**3. 都验证了"诚实标注"的价值**。三个案例里没有一个"全知视角"的结论：
ChatGPT 桌面版是部分完成（约 1/4 源文件），OpenCode 有 5 个原生交接点到此为止，
PCL2 的类型名误判被修正后写进了报告。**过程里的修正没有被藏起来，而是成了报告最有说服力的部分。**

**4. 都撞上过"名字会骗人"**。文件名（"2.1" 实为 2.13.1.1）、类型名（`PageLinkMain` / `MySkin`）、
文件大小（497 字节的转发 stub 曾给出"全部为假"的误导性结论）——三个案例各有一个这样的故事。
交叉验证不可跳过。

**5. 规模决定预期**。一句话总结三个案例的适用面：

| 目标类型 | 规模 | REA 的表现 |
| --- | --- | --- |
| .NET 单文件 | 5.5 MB | 全量反编译路径最顺，读起来最容易 |
| Electron 中等规模 | 146 MB | **应用图谱完整产出**（semantic 层截断于节点上限）——最合适的区间 |
| Electron 超大归档 | 567 MB | 部分完成（容量耗尽有明确标注），需配合直接解析 |

三个案例都是**静态完成**：没有执行过目标程序的任何一行代码，没有绕过任何技术保护措施。
这不是方法论的限制，是本手册推荐的默认姿势——对"学习设计思想"这个目的，
静态分析得到的信息已经足够，而且边界清晰、可复核。
