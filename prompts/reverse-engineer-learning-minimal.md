# 逆向学习提示词 · 纯学习版

> ⚠️ **仅对你有权分析的目标使用**（你自己的软件、开源项目、你购买并有权分析的产品）。
> 模板本身**不含**账号登录、授权/付费机制、密钥或隐私数据的分析步骤，也不产出可复现的绕过细节——
> 这些不在本手册范围内，遇到请跳过。
>
> 只要你**看懂 + 学到**，不需要往自己项目上映射。
> 适合"这个软件做得不错，我想看看它怎么实现的"。

---

## 主提示词（完整版，复制这一段）

````text
# 任务：逆向分析一个应用，看懂它的「<要学的功能>」是怎么做的，并找出它做得好的地方

## 目标
- 应用路径：<填入绝对路径>
- 想看的功能：<填入；如果没想好，写"你先通读一遍，告诉我它有哪些值得看的设计">
- 我不需要往自己项目上映射，只要**看懂 + 学到**。

## 工作原则（重要）

1. **静态分析，不要运行它**。你看不到实际界面——关于 UI 的判断只能从 XAML/样式/布局代码推断，标【推断】。
2. **每条结论必须标注证据等级**：
   - 【观测】= 直接看到了（源码、反汇编、字符串原文、文件偏移）
   - 【推断】= 根据结构/命名/行为推断的
   不允许不标注就直接下结论。
3. **讲清楚"为什么这么做"**，不只是"它做了什么"。看到一段设计，要回答：
   - 它解决什么问题？（想象没有它会怎样）
   - 为什么选这个方案而不是更简单的方案？
   - 代价是什么？（性能、复杂度、维护性）
4. **要能看懂**：如果涉及我不熟悉的领域（协议、算法、平台机制），
   先用一两句解释背景，再讲它怎么做。

## 阶段 0：侦察 + 先告诉我有什么值得看

不要一上来就深挖。先做类型识别（这是什么技术栈），
然后**快速通读一遍**，给我一份"菜单"：

> "这个应用里有 5 处设计我觉得值得看：
> ① 它的 X 机制（因为……）
> ② 它的 Y 处理（这是难点）
> … 你想先看哪个？或者我按这个顺序全部展开？"

**如果我说"你先通读"，就直接按你的判断展开，不用等我选。**

技术栈识别表：

| 特征 | 类型 | 分析路径 |
|---|---|---|
| PE + `.NET` 元数据 | .NET 托管程序集 | 可全量反编译，最容易读 |
| PE + 无托管元数据 | 原生二进制 | 需要 Ghidra/IDA（先问我有没有） |
| `.asar` / 含 `resources/app` | Electron/JS | 可直接读 JS 源码 |
| `.jar` / `.apk` | Java / Android | JADX |
| 含 `go build` 标记 | Go 二进制 | `inspect-go-binary` |
| 含 `.dep-v0` 段 | Rust 二进制 | `inspect-rust-binary` |

**侦察完先汇报"这是什么 + 我看到哪些值得看的地方"。**

## 阶段 1：怎么读

### 通用第一招：字符串扫描（**产出/成本比最高**）

```
成熟应用的日志文案是"自带文档"——从字符串能直接读出工作流。
例：一个下载系统会留下 "分析支持库文件" → "下载支持库文件" →
    "分析资源索引" → "下载资源索引"，顺序即流程。

.NET 要按 UTF-16LE 解码（不是 ASCII），中文/URL 才出得来。
中文串和 URL 尤其有价值：URL 直接暴露它连了哪些服务。
```

### .NET 应用：优先全量反编译

```bash
dotnet tool install --global ilspycmd   # 若未安装
ilspycmd -p -o <输出目录> "<目标>"       # -p = 整个项目，产出可读源码
# ⚠️ 反编译出的语言可能与原文不同（VB.NET 会变 C#），但命名和结构准确。
#    对"学习设计"来说完全够用——你要学的是思路，不是语法。
```

### Electron 应用：直接读 JS

```bash
rea analyze-javascript-application "<asar或目录>" --format json > evidence.json
# 若报 integrity_mismatch（打包时会二次签名，正常）：
#   加 --integrity-policy record-and-continue
# ⚠️ evidence 可能几百 MB，先投影成 summary 再看
```

## 阶段 2：看什么（这才是重点）

**不要只描述"它做了什么"，要按这几类去找"值得学的地方"**：

### ① 它怎么组织复杂度
- 有没有一套统一的抽象，把一堆相似的东西收敛了？
  （例：一个框架让"下载/安装/启动"都走同一条路）
- 有没有把"容易出错的顺序"固化成结构？
  （例：强制"先分析再执行"，而不是散落各处）

### ② 它怎么处理"必然会失败的事"
- 网络断了怎么办？重试策略是什么？
- 失败怎么告诉用户？（只是报错，还是告诉用户"下一步做什么"？）
- 有没有"可恢复的失败"和"不可恢复的失败"的区分？

### ③ 它怎么处理"用户的旧数据"
- 升级后老配置怎么办？
- 它怎么判断"用户想要什么"？（问用户？还是从已有文件推断？）

### ④ 它怎么让"慢"变得可以忍受
- 进度怎么算的？（很多应用的进度条是假的，它是不是真的？）
- 长任务能取消吗？取消后资源回收干净吗？

### ⑤ 它怎么做到"看起来简单"
- 有没有把复杂逻辑藏在背后，只给用户一个按钮？
  （例：一键联机背后是 P2P 穿透 + NAT 类型诊断）

### ⑥ 它有没有"性格"
- 文案怎么写的？（是冷冰冰的"操作失败"，还是有话直说？）
- 有没有为特定场景做的贴心处理？（例：崩溃时违背用户设置把窗口弹回来）

### ⑦ 它的工程细节
- 常量集中管理吗？（所有动画时长在一处，还是散落各处）
- 调试信息泄漏吗？（很多应用会泄漏源码路径——这对你是礼物）
- 有没有"为什么这么写"的痕迹？（命名、结构能反映设计意图）

## 阶段 3：输出格式

```markdown
# <应用名> 的「<功能>」是怎么做的

## 这是什么
技术栈、版本、规模（几行代码/几个类型/多大）

## 它要解决的问题
用一两句话，不用术语。（想象你是第一次听说这个功能）

## 它是怎么做的
按流程/结构讲，配具体的类名、方法名、字符串原文。
【观测】和【推断】要标清楚。
关键处要解释"为什么这么做"。

## 我觉得做得好的 N 个地方
每条：
- **是什么**（具体机制）
- **解决了什么问题**（没有它会怎样）
- **妙在哪**（为什么不是用更简单的办法）
- **代价**（它付出了什么）

## 如果我要自己做
不建议抄什么，不建议用什么——这把"学习"变成"你能带走的东西"。
（不是往项目上映射，是"如果哪天真要做类似的事，我会记得什么"）

## 复现指南
我用了哪些命令，别人怎么重跑一遍
```

## 已踩过的坑（照做省时间）

1. **.NET 全量成员提取会失败**（元数据超 64MB）→ 用 `--type` 逐个类型提，
   或者干脆全量反编译。
2. **类型名不要靠猜**——按类型名推断功能经常出错。
   **名字会骗人，字段和方法不会**：拿到可疑的类型，先看它的字段和方法。
3. **大目标的 evidence 是几百 MB**——用 `--filter-output` 或视图投影。
4. **`--token-limit` 不能与结构化输出同用**，用 `--filter-output`。
5. **asar 完整性校验失败是正常的** → `--integrity-policy record-and-continue`。
6. **在含 `"type": "module"` 的项目里写脚本要用 `.cjs` 后缀**。
7. **Git Bash 的 `/tmp` 与 Node 解析的路径不同**——放项目内用相对路径。
8. **传 `/` 开头的参数给 Node 脚本时加 `MSYS_NO_PATHCONV=1`**。
9. **调试字符串常泄漏源码路径**——搜 `E:\` 或 `/home/` 开头的串，
   能还原项目的目录结构（很有价值）。
10. **反编译产物的语言可能与原文不同，但结构准确**。

## 现在开始

先做阶段 0，告诉我"这是什么 + 有哪些值得看的地方"。之后按我的选择展开，
或者我让你全展开你就全展开。
每一步有重大发现时简短说一次，不要憋到最后。
可以开子 agent 并行，但按"功能维度"切分（一个 agent 管一个功能）。
````

## 精简版（约 700 字，日常用这个）

````text
逆向分析 <目标路径>，看懂它的「<要学的功能>」是怎么做的，
并告诉我它有哪些做得好的地方。我不需要往自己项目上映射，只要看懂 + 学到。

要求：

1. 静态分析，不要运行它。看不到实际界面，UI 相关只能说代码层面的事实。
2. 标注证据等级：每条结论标【观测】（看到源码/反汇编/字符串原文）
   或【推断】（根据结构猜的）。
3. 讲清楚"为什么这么做"，不只是"它做了什么"——它解决什么问题、
   为什么不用更简单的办法、代价是什么。
4. 涉及我不熟的概念（协议/算法/平台机制），先用一两句解释背景。

步骤：

**第一步，先侦察**。判断它是什么技术栈（.NET / 原生 PE / Electron-JS /
Go / Rust / Java），然后快速通读一遍，给我一份"菜单"：
"这个应用里有 N 处设计我觉得值得看：①… ②… 你想先看哪个？"
（如果说"你先通读"就直接全展开，不用等我选。）

**第二步，字符串扫描（任何类型都做）**。
成熟应用的日志文案是自带文档——搜二进制里的字符串（.NET 按 UTF-16LE 解码）
能直接读出工作流。中文串和 URL 尤其有价值（URL 直接暴露它连了哪些服务）。

**第三步，按技术栈读**：
- .NET：优先全量反编译（`ilspycmd -p -o <目录> <目标>`），
  产出可读源码，对"学设计"完全够用（语言可能变但结构准确）。
- Electron/JS：`rea analyze-javascript-application <路径> --format json`，
  报 integrity_mismatch 就加 `--integrity-policy record-and-continue`。
  输出可能几百 MB，先投影成 summary。
- 其他：告诉我。

**第四步，重点找这几类"值得学的地方"**：
① 怎么组织复杂度（有没有统一抽象收敛相似的东西）
② 怎么处理必然的失败（重试、怎么告诉用户、可恢复 vs 不可恢复）
③ 怎么处理用户旧数据（升级后的配置怎么办、怎么判断用户想要什么）
④ 怎么让"慢"可忍受（进度是真的吗、能取消吗、资源回收干净吗）
⑤ 怎么做到"看起来简单"（复杂逻辑藏背后，只给一个按钮）
⑥ 有没有"性格"（文案风格、为特定场景做的贴心处理）
⑦ 工程细节（常量是否集中、有没有泄漏调试信息）

**第五步，输出**：
① 这是什么（技术栈/版本/规模）
② 它要解决的问题（一两句大白话）
③ 它是怎么做的（带类名/方法名/字符串原文，标证据等级，解释"为什么"）
④ 做得好的 N 个地方（每条：是什么 / 解决什么问题 / 妙在哪 / 代价）
⑤ 如果我要自己做（能带走的心得，不是往项目上映射）
⑥ 复现指南

约定：先给我"菜单"再展开。每有重大发现简短说一次。
可以开子 agent 并行，按"功能维度"切分。
````

## 两份提示词怎么选

| 你的目的 | 用哪份 |
|---|---|
| 纯粹好奇 / 想学设计 | **本文件（纯学习版）** |
| 要写进自己项目 | [reverse-engineer-learning.md](reverse-engineer-learning.md)（完整版，带"可借鉴性"一节） |

**两者最大的区别**：纯学习版把输出第四节从「**对我的项目**：可借鉴/需改造/不能照搬」
换成了「**我觉得做得好的地方**：是什么 / 解决什么问题 / 妙在哪 / 代价」。
——不问"我能抄什么"，而问"它妙在哪、代价是什么"。

## 一句提醒

**"做得好的地方"要诚实**。如果分析下来发现某处其实很平庸、
或者有更好的做法，就直说。**吹捧没有学习价值。**
一份好的学习报告里，"它这里其实做得不好"往往比"它这里很棒"更有用。
